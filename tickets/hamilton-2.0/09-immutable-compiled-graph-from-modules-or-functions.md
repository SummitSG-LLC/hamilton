# Compile modules or explicit functions into an immutable compiled graph, reached through `Builder` and `Driver` with the switch on

## Why

On 1.x, building a graph has side effects, and the graph it gives can change afterwards. `@config.when` renames the user's function in place, so a function whose name holds more than one double underscore gets a different node name on the second build. The graph keeps the caller's config dict by reference, and it stores adapters and asks them about edge types while it is built. The task-based executor later rewrites node callables on that same graph. A cyclic graph builds without error and fails at run time with `RecursionError`; the check that would find the cycle needs `networkx`. A graph can be built only from modules: explicit functions go through `ad_hoc_utils.create_temporary_module`, which drops keyword-only defaults and leaves a made-up module in `sys.modules`.

This Ticket adds the new compiler: `compile(sources, config)` takes modules or explicit functions and returns a compiled graph that cannot change, holds no adapter, and knows the source file and line of every node. With the switch on, `Driver` and `Builder` get their graph from it. Everything the new runtime, the catalog and the tools do later reads this compiled graph, so its agreement with the 1.x graph is what makes old and new comparable.

## Authority and intent

Dev-iL assigned this effort and ruled what the prototype is: a new compiler and a new runtime "reached through the existing Builder/Driver behind an opt-in switch. Old paths stay as the reference for behavior and speed comparisons." That ruling fixes one part of the definition of done, marked there. The rest is the plan's working reading of the outline ("accept both modules and explicit functions", a compiled graph that "stays unchanged during a run and can be shared by independent runs", "retain source locations for generated nodes", "preserve unrecognized metadata") and may be revised on evidence. Dev-iL merges the pull request. The shape of the compiled graph's types, the name of the `Builder` method that takes functions, how a cycle is reported to the caller, and how the agreement test collects its modules are yours to decide and report.

## Scope

A new package, `hamilton/compiler/`, and the branch in `Driver` and `Builder` that uses it when the switch is on. The 1.x graph building stays in place and is not rewritten. Reuse the decorator pipeline (`resolve_nodes` in `hamilton/function_modifiers/base.py`) and the hint boundary from Ticket 08. Leave these to their own Tickets: structured diagnostics with codes (Ticket 18), the catalog, requirements queries and the JSON artifact (Ticket 19), the CLI, LSP and MCP tools (Ticket 20), and running the compiled graph (Tickets 07 and 10). The plan also leaves out declared-config rules, default-producer rules, and any change to how `@check_output` nodes are named or exposed: the compiled graph has the same validator nodes as the 1.x graph.

## Watch out for

- The switch. This Ticket does not depend on Ticket 07, which also works behind the switch. If the switch already exists on `2.0` when you start, use it. If it does not, add it here as the effort's front file describes it: a `Builder` option for one Driver and an environment variable for a whole test run. There is one switch; do not add a second. With it on, a Driver never falls back to a 1.x path, so until the new runtime can execute, executing with the switch on fails with an error that names what is unsupported.
- `@config.when` sets `__name__`, `__original_name__` and `__config_decorated__` on the user's function when it resolves. The compiler must leave the function as it found it. If you change the shared decorator code to do that, the 1.x build path changes too: either keep its behavior with the switch off or add migration instructions.
- On 1.x the config is aliased in two places: a dict passed straight to `Driver(...)` is kept by reference, and `Builder` hands its own dict to the Driver, so a later `with_config` on the same `Builder` reaches a Driver already built. `Builder.with_config` copies the dict it is given. Test the wording of the definition of done and these two cases as well.
- The 1.x graph asks its adapters whether two edge types match while it is built. The compiled graph must hold no adapter. So the type comparison is either handed to the compiler for the length of one compile and not stored, or applied by whoever builds the Driver. If Ticket 07 is merged, its contracts name the owner of "how edge and input types are compared"; use that.
- `Annotated`. The outline reports that `Annotated[float, metadata]` is rejected today. A probe at the branch point built and ran a graph with `Annotated[float, "m"]` on a return type and on a parameter. So start with a characterization test that finds where rejection or loss happens; the decorators that read hints without extras are the likely place. If nothing rejects or drops it, the `Annotated` item is already met and its tests stay as regression tests.
- The existing route for explicit functions copies each function without its `__kwdefaults__`. Do not build the new route on it.
- Compile must not import or need `networkx`. The standard library's `graphlib` is a reference for ordering and for finding a cycle.
- Materializers given to `Builder` are added to the 1.x graph after it is built. A compiled graph cannot be added to, so adding nodes means producing a new compiled graph. Ticket 14 makes materialization work on the new runtime; do not close that door here.
- `compile` returns the graph and what it found wrong. Ticket 18 gives that second part its structure and codes. Keep what you return here small enough that Ticket 18 can replace it.
- What the new `Builder` method for functions does with the switch off is not settled by the plan. Failing with a clear error that names the switch leaves the 1.x paths untouched. Say what you chose, and add migration instructions if 1.x code behaves differently.
- The agreement test must cover every module the core suite builds a graph from. Collect that list with a script or a fixture a reviewer can rerun, not by hand.
- Sketch the compiled graph's shape, then one structurally different shape, and keep the better. Make a changed compiled graph unrepresentable through the public API, and test at `compile`, `Builder` and `Driver`, not at internals.
- The typed consumer script must call `compile`, read the compiled graph, and use the new `Builder` method, and still pass pyrefly.
- `hamilton/graph_types.py` holds `HamiltonGraph`, a public inspection view. The outline says it is "not a settled executable graph contract." Do not make it the compiled graph.

## Suggested approach

This is advice; discard it if you find better. Write the characterization test for `Annotated` and the agreement test first, both failing. Have `compile` copy or wrap functions before the decorator pipeline touches them, run `resolve_nodes`, and freeze the result into node definitions that carry name, types, tags, callable, dependencies and source locations, with a config snapshot taken by copy. Detect cycles while ordering the nodes. Then route `Driver` and `Builder` through `compile` when the switch is on, and run the agreement test over every collected module.

## Definition of done

Fixed by the owner's ruling that the new compiler is "reached through the existing Builder/Driver behind an opt-in switch", with the old paths as the reference:

- With the switch on, `Driver(...)` and `Builder().build()` obtain their graph from the compiler.
- For every module the existing core suite builds a graph from, the compiled graph and the 1.x graph built from the same module and config agree on node names, types, tags and edges. Each difference is one that the immutability items or the source-location and cycle items below require, and it is listed with its reason. An agreement test over those modules shows this, and a scratch change that makes the compiler drop one node is seen failing it.

The rest is the plan's working reading of the outline, and may be revised on evidence as long as the result above holds:

- Modules and explicit functions give the same graph. Compiling a module and compiling the list of that module's functions give graphs with the same nodes, edges, types and tags. Functions passed explicitly keep their keyword-only defaults. `Builder` accepts explicit functions. No temporary module is left in `sys.modules`. An equivalence test over the modules in `tests/resources/` that the suite already builds graphs from shows this.
- A compiled graph cannot change. The public API offers no way to alter a compiled graph's nodes, edges, tags, callables or config, and each attempt raises. The compiled graph holds no adapter.
- Compiling changes nothing else. Compiling the same sources and config twice gives equal graphs, and leaves each user function's `__name__` and attributes as they were before the first compile. With the switch on, changing the config dict passed to `Builder` after `build()` does not change the built Driver. Tests cover each clause of this item and the one before, and include a module that uses `@config.when` with names that contain more than one double underscore.
- Nodes know where they came from. Each node of a compiled graph gives the source file and line of the function or functions it came from, including nodes generated by decorators. Tests over decorated fixtures show it.
- Cycles are reported at compile time. Compiling sources that contain a cycle reports the cycle's node names, without needing `networkx`. A test over a cyclic fixture shows it.
- `Annotated` metadata survives. For `Annotated[T, *metadata]` on a return type or a parameter, edge and input type checks use `T` on both sides, and the compiled node keeps the metadata unchanged, including through the decorators that today read hints without extras. A characterization test, written first, records where the code at the branch point rejects or drops `Annotated`; its recorded result is in the pull request, beside tests for the two behaviors.
