# Make the core install, import and run without pandas or numpy

## Why

`apache-hamilton` lists pandas and numpy as required dependencies. A user who writes plain Python functions, or who uses another dataframe library, still installs both and pays for them at every import: at the branch point `import hamilton.driver` took 431 ms, and pandas was 287 ms and numpy 78 ms of it. The default result differs by entry point as well: `Driver(config, module).execute(...)` with no result builder returns a pandas DataFrame, while a Driver from `Builder` returns a dict. The outline proposes "a minimal `apache-hamilton` install with a plain dictionary result default; pandas results remain available through an explicit result builder and optional installation", and warns that this change "must be listed and prepared for, not treated as an invisible refactor". This Ticket makes the core on `2.0` install, import and run with neither library present. It moves the pandas and numpy pieces into plugin modules behind optional extras, makes each old import path fail with an error that says where the name went, makes a dict the default result everywhere, and measures the import time.

## Authority and intent

Dev-iL assigned this effort and chose a prototype that includes a "core without pandas/numpy". That result is fixed. Three things are the plan's working reading and may be revised on evidence. First, that core modules import the two libraries at no scope, function bodies included. The outline permits function-local imports for loading providers; the plan is stricter because Dev-iL prefers fixing a root cause over machinery that moves a cost to another time, and a lazy import moves the import cost to call time. An exception may stay if its reason is recorded. Second, the form of the optional pieces and of the old-path errors. Third, the order: this change lands on `2.0` first, and Ticket 24 then back-ports the relocation to `main` as a non-breaking 1.9x step. The order agreed earlier for apache/hamilton issue #918 was the reverse; the plan changed it because a fork branch cannot wait for upstream review, and the end state is the same. If Dev-iL reverses the order, Ticket 24 runs first and this Ticket shrinks to a deletion. Dev-iL retains the merge and the go for any outward-facing act, which includes publishing a package and anything written on `apache/hamilton`. Yours to choose: the plugin module names, the marker's name, how `@check_output` finds the moved validators, and how an old path raises its error.

## Scope

A change across the core, worth doing in one pull request because the pieces only prove themselves together: the required dependencies and two new extras named `pandas` and `numpy` in `pyproject.toml`; the core modules that import either library; the plugin modules that receive the moved pieces; a test marker; a CI job; the migration instructions; and one harness measurement. These changes apply with the switch off as well as on, so their migration instructions go in the main part of the migration document. Out of scope: any redesign of how extensions are discovered or loaded (Ticket 25 surveys that, and the rules below keep entry-point discovery out); a new provider distribution; any change to how `@check_output` nodes are named or exposed; and the 1.x relocation behind warnings, which is Ticket 24 on a branch off `upstream/main`. Modules under `hamilton/plugins/`, `hamilton/contrib/` and `hamilton/experimental/` may go on importing both libraries.

The only allowed differences are changes that have migration instructions and fixes that are also proposed for `main`. - **Left out by the plan; the owner may revise on evidence.** `requires-python` stays `>=3.11`. No compiled or native code. No entry-point plugin discovery and no new provider distribution. No declared-config or default-producer rules. No change to how `@check_output` nodes are named or exposed. No driver-script emitter and no new renderers. No runtime branching or loops.
- **Outward-facing acts wait for the owner's go, each time.** Do not push a branch named `2.0` to the fork, do not push, open a pull request, or write an issue, comment or discussion post on `apache/hamilton`, and do not publish a package, unless the owner said go for that specific act. Stop at the prepared state (a local branch, a drafted description) and report what is waiting. Pull requests from a work branch into `2.0` on the fork need no separate go once `2.0` exists there.
- **The project's checks pass.** `uv run prek run --all-files --hook-stage pre-merge-commit` exits 0. `uv run pytest tests/ --ignore tests/integrations` exits 0 on Python 3.11 and on the newest Python in the CI matrix. On a branch that carries the pyrefly configuration, the pyrefly check exits 0 when run with the command and environment the static-checks job uses. Every CI job and step on the pull request passes, the integration and plugin steps included.
- **Every breaking change gets migration instructions in the same pull request.** A breaking change is any change after which code that works on Hamilton 1.90 fails, warns differently or returns a different result. Add the instructions to `docs/migration-to-2.0.md`: in its main part when the change applies with the switch off, in its section for the day the new compiler and runtime become the default when it applies only with the switch on. (Owner's requirement.)
- **The runtime core names no adapter, and every adapter is removable.** The coordinator, plan, run state, contracts and inline backend import no thread backend, coroutine backend, caching module or integration, and do not branch on the identity of one. - **Code holds up for its users and maintainers.** Correct results for supported inputs; a clear error for each new failure mode; a bound or cleanup path for anything that grows per run or per item; tests that would fail on a plausible wrong implementation and take expected values from a source independent of the code under test; accurate type hints on new public functions; correct documentation; the ASF license header on each new file (added by hand under `docs/`).

- **One pull request per Ticket, and it shows the change working.** The description's top reads in about a minute: what changed and why, how it was shown working, decisions made, debt left. ## Watch out for

- At the branch point, pandas or numpy is imported at the top of the Driver module, `hamilton/base.py`, `hamilton/models.py`, `hamilton/io/utils.py`, `hamilton/log_setup.py`, the macros decorators and the default validators, and inside a function in the cache's fingerprinting. That list will be stale when you read it. Find the present one with a search of the syntax trees.
- The Driver's own simple adapters inherit from the dataframe adapter. `DefaultAdapter` extends `SimplePythonGraphAdapter`, which extends `SimplePythonDataFrameGraphAdapter`, which extends `PandasDataFrameResult`. Moving the dataframe adapter means giving the simple adapters a new base. A comment in the code already asks for that.
- `Driver(...)` called directly appends `PandasDataFrameResult` when no result builder is given. `Builder` already defaults to a dict. Ticket 04 listed this default change as one this Ticket owns.
- `@check_output` imports the default validators at the top of its module. That module imports both libraries and holds the pandas validators and the scalar validators in one hand-kept list. A check on a scalar must work with neither library installed, and a check on a pandas type must still work once the extra is installed. How the moved validators are found is yours to design, without entry-point discovery.
- Importing the decorator package tries to import every known extension, the pandas and numpy extension modules included, and skips those that fail to import. In an environment that has pandas, `import hamilton.driver` therefore still imports pandas through that path after this Ticket. This Ticket does not redesign that loading. The environment variable `HAMILTON_AUTOLOAD_EXTENSIONS=0` turns it off.
- That has a consequence for the import-time verdict. The commit before this change cannot be installed without pandas and numpy, so the two sides cannot have identical environments. Measure each side in an environment that holds its own required dependencies and nothing else, on the same machine and Python build, alternately. State the two environments in the verdict. Report as well what the new side measures in an environment that has pandas installed.
- The old side of the comparison is the commit before this change, run from that commit. The stored 1.x result file from Ticket 03 is a reference record and never one side of a comparison. Name the limiter from a profile of the import. A gain larger than the share pandas and numpy had (365 of 431 ms at the branch point) is a measurement fault until explained.
- A search of syntax trees finds direct imports only. A core module that imports a plugin module that imports pandas passes the search and fails in the fresh environment. Both checks are needed, and neither replaces the other.
- An import under `if TYPE_CHECKING:` is still an import in the syntax tree. Under the plan's reading it is an exception that needs its reason recorded. Do not swap an import for a string annotation that can never resolve; that hides the dependency.
- Several core signatures name `pd.Series` or `pd.DataFrame` (the model base class, the macros decorators, the IO utilities). Each either moves with its pandas piece or changes its annotation, and a changed public annotation may be a breaking change.
- `hamilton/log_setup.py` calls numpy to silence floating-point warnings. Read why that call was added (its commit and pull request) before you remove or move it.
- Keep each moved name at its 1.x location as something that raises an error naming the new import path and the migration instructions. A deleted name gives the user a bare "cannot import name", which tells them nothing.
- The version on `2.0` is `2.0.0.dev0` (Ticket 04), and the deprecation mechanism ignores the pre-release part of a version. Anything you schedule through it for 2.0.0 fires now.
- The names moved here are used beyond the core: `hamilton/async_driver.py`, the Dask, Spark and narwhals plugins, the experimental cache, one contrib dataflow, and possibly `ui/sdk`, the examples that CI runs and the docs. For each moved name, search separately for calls, type references, string literals, dynamic imports, re-exports and tests.
- Ticket 24 must use the same new locations on `main`, where pandas is still required. Choose plugin module names that can exist on 1.x.
- A marker cannot rescue a test module that imports pandas at its top: collection fails before any marker is read. Many core test modules import pandas or numpy at the top today. The job needs a way to collect the suite without them, and the list of tests that need them is part of the evidence.
- CI's ordinary jobs go on installing pandas. The job this Ticket adds is separate: a fresh environment, outside the repository, holding only the core wheel and its required dependencies. Ticket 01's installed-wheel job is the pattern.
- `driver.py` and `base.py` are long files. Before you restructure one, remove its dead code, unused imports and debug logs in a separate commit.

## Suggested approach

This is advice; discard it if you find better. Write the two checks first and see them fail: the syntax-tree test, and the fresh-environment job with a scratch `import pandas` in a core module. Add the new plugin locations beside the old ones, move the callers in batches, then turn each old location into a name that raises. Split the scalar validators from the pandas validators before touching `@check_output`. Change the default result last, with its migration instructions. Measure the import time once the fresh-environment job passes.

## Definition of done

Fixed by the owner's choice of a prototype that includes a "core without pandas/numpy":

- In a fresh environment that holds only the core wheel and its required dependencies, neither pandas nor numpy is installed.
- `import hamilton.driver` succeeds there.
- Every core test that needs neither library passes there, including a `@check_output` check on a scalar. The tests that do need them are selected by a marker and listed.
- Neither `pandas` nor `numpy` is in `sys.modules` afterwards.
- A CI job on `2.0` asserts all of the above. A scratch top-level `import pandas` in a core module is seen failing that job.

The rest is the plan's working reading, and may be revised on evidence as long as the result above holds:

- **Core modules import the data stack at no scope.** The region is every module under `hamilton/` outside `hamilton/plugins/`, `hamilton/contrib/` and `hamilton/experimental/`. None of them imports pandas or numpy at any scope, function bodies included. An exception stays only with its reason recorded as debt in the pull request description. A test in the suite searches the region's syntax trees for those imports.
- **The data-stack pieces are optional, and old import paths fail clearly.** The pandas and numpy result builders, the dataframe graph adapter and the pandas validators are importable from plugin modules once the `pandas` or `numpy` extra is installed. Importing a moved name from its 1.x location raises an error that names the new import path and the migration instructions. `Driver(config, module).execute(...)` with no result builder returns a dict, and so does an `AsyncDriver` constructed with no result builder, which has the same implicit pandas default on 1.x. Tests show all of these, in an environment with the extras and in one without.
- **Import time is faster.** The harness's import-time scenario is measured against the commit before this change, in the way the rule below on performance claims requires, and the verdict is "faster". The evidence is the harness output files. If the verdict is anything else, the Ticket is not done: name the limiter and report it.
