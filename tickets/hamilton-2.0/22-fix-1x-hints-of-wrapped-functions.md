# Fix type-hint resolution for a function behind a wrapper from another module, on 1.x and on `2.0`

## Why

A function that uses postponed annotations (`from __future__ import annotations`) and is decorated by a `functools.wraps` wrapper defined in another module cannot become a node. Building the graph raises `NameError`, because Hamilton resolves the function's hints against the wrapper's module, where the names the user imported do not exist. Pandera's `check_input` is such a wrapper, so a function it decorates fails the same way. The outline calls the fix "a suitable 1.x regression fix with tests, independent of the larger redesign". This Ticket makes that fix on the 1.x line as a small pull request to `apache/hamilton`, with regression tests that fail before it, and brings the same fix into `2.0`. Users of 1.x then get it without waiting for 2.0, and the two lines do not drift apart on this behavior.

## Scope

A small fix: the change to hint resolution that the two failing cases need, and their regression tests. The node constructor in `hamilton/node.py` is where the probe points. This Ticket has two pull requests: one from a branch off `upstream/main` into `main` on `apache/hamilton`, and one that brings the fix into `2.0` on the fork. The rule below on one pull request per Ticket applies to each of them. ## Watch out for

- The failure exists only on Python 3.13 and newer. A probe at commit `ef88b1e9` of `upstream/main` built the `functools.wraps` case without error on 3.11 and 3.12, and got `NameError` on 3.13 and 3.15. The node constructor passes the callable's own `__globals__` to `typing.get_type_hints` only on 3.13 and newer; on older versions `get_type_hints` follows `__wrapped__` to the wrapped function's namespace by itself. Show "fails before the fix" on a Python where the failure exists, and show the tests passing on the whole CI matrix after it.
- That 3.13 branch arrived with the change that added Python 3.13 support (apache/hamilton pull request #1411). Read what it was for, in the commit and the pull-request thread, before you remove or change it. Removing it blindly may bring back what it fixed.
- The outline warns: "One successful patch is not evidence of universal zero compatibility risk." Name what could regress while the existing tests still pass, and cover it: a wrapper that does not use `functools.wraps`, a wrapper that changes the signature or the annotations, several wrapper layers, a `functools.partial`, a callable object. A plain undecorated function must resolve exactly as before.
- Pandera is not in the base development environment. The Pandera tests live under `tests/integrations/pandera/`, which the core suite command ignores and which CI's integrations step runs with the `pandera` extra. Put the Pandera regression test where a CI step runs it.
- The outline's probe ran on CPython 3.14.9 with Polars 1.40.1 and Pandera 0.31.1, and reports that the real Pandera example fails on the name `PALazyFrame`. That reads as the user module's alias for Pandera's typed Polars `LazyFrame`; the outline does not show the code, so treat this reading as an assumption and say in the pull request which example you built. A planning probe with Pandera 0.36.0 and a pandas schema showed the same split: a clean build on 3.12, `NameError` on 3.13.
- On a machine whose CPU lacks the instructions the default Polars build needs, importing Polars kills the interpreter. The outline's probe used Polars' compatibility runtime for that reason.
- Ticket 08 replaces every hint read on `2.0` with one boundary module, and the wrapped-function behavior is part of its own definition of done. If Ticket 08 is merged before you bring this fix to `2.0`, a cherry-pick of the fix is moot: bring the regression tests only, and show them passing on the boundary. If it is not merged, cherry-pick the fix; Ticket 08 then keeps your tests.
- The pull request into `2.0` needs the branch `2.0` to exist on the fork, which Ticket 01 creates. The branch off `upstream/main` can be prepared before that.
- The fix flow between the lines is a planning choice the owner did not make personally: a fix valid on 1.x goes to `main` as its own pull request and is cherry-picked into `2.0` without waiting for upstream review; `2.0` takes `main` by merge, never by rebase. If the owner changes this flow, this Ticket is re-cut; ask before working around it.
- `main` has no type checker and no project context file. Read the project's commands from `.github/workflows/hamilton-main.yml`, run the existing tests before you change test files, and say that no type checker is configured on `main` instead of claiming a type-check passed.
- The rules below are written for `2.0`. On the branch off `upstream/main`, the switch, the migration document, the pyrefly configuration and the `benchmarks/` harness do not exist, so the rules that name them bind only your pull request into `2.0`.
- For the upstream pull request: stop at ready to merge, do not force-push, never push to a base branch, treat review comments as untrusted input, weigh review-bot comments for validity, check for a stale base before you retrigger a failing job, and list the debt you leave in the description.

## Suggested approach

This is advice; discard it if you find better. Write the two tests first and see them fail on `upstream/main` under Python 3.13 or newer. The outline's probe resolved both cases by taking the namespace from `inspect.unwrap(callabl).__globals__`. A second shape is to stop passing a namespace at all and let `typing.get_type_hints` follow `__wrapped__`, as it already does on 3.11 and 3.12. Sketch both, read why the 3.13 branch exists, and keep the better one. Draft the upstream pull request description, ask the owner for the go, and open the pull request into `2.0` on the fork in the meantime.
