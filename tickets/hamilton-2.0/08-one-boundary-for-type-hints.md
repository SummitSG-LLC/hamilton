# Resolve every function's type hints in one boundary module, and drop `typing_inspect` from the core

## Why

The core reads a function's type hints in many places, and the places do not agree. Building one node calls `typing.get_type_hints` three times. Several decorators call it again, without the option that keeps `Annotated` metadata. About 60 calls to `typing_inspect` functions are spread over five core modules. Two results of this were measured. A function with postponed annotations that is decorated by a `functools.wraps` wrapper defined in another module fails to build with `NameError`; the outline calls this the wrapper-global failure. And build time, 103 ms per 1,000 nodes at the branch point, goes to `typing.get_type_hints` and `inspect.signature`.

This Ticket puts every read of a function's annotations behind one boundary module. The 1.x build path and the new compiler both use it, so both sides of the switch see the same hints. Each function's hints are resolved once per build. A name that cannot be resolved becomes a recorded state with its namespace, in place of a crash at build time or a comparison of strings.

## Authority and intent

Dev-iL assigned this effort. No ruling of Dev-iL's was made for this Ticket in particular: its whole definition of done is the plan's working reading of the outline, which asks for "One annotation-resolution boundary and better unresolved-reference diagnostics" and says to "Preserve unresolved annotations with their namespace and an explicit unknown state." That reading may be revised on evidence. Dropping `typing_inspect` was chosen in planning without asking Dev-iL, on the strength of Dev-iL's standing preference for a maintained alternative when an upstream looks abandoned. Dev-iL merges the pull request. The boundary module's name and interface, the order in which callers move to it, and how the search test treats its edge cases are yours to decide and report.

## Scope

A refactor of the core's hint reading: one new module, edits to each core module that reads annotations or calls `typing_inspect` (node construction, `hamilton/htypes.py`, the decorators under `hamilton/function_modifiers/`), the dependency list in `pyproject.toml`, tests, and migration instructions. Behavior stays the same except for the two changes the definition of done names: wrapped functions resolve, and an unresolved name no longer stops the build. The region excludes `hamilton/plugins/`, `hamilton/contrib/` and `hamilton/experimental/`; do not migrate their hint reads. Do not start the compiler here; that is Ticket 09. Do not change how Hamilton compares or normalizes types: the outline says annotation inspection "does not replace Hamilton's full type normalization and validation."

## Watch out for

- Treat this as a behavior-preserving step for everything except the two named changes. Before you start, write down what must stay the same (the input and output types every node and decorator sees, for every fixture the suite builds) and how you will check it. Add characterization tests where the suite has a gap. List every caller. Add the boundary beside the old reads, move callers in batches, then remove the old reads.
- The 1.x build path uses the boundary, so the rule that the 1.x paths stay applies. The wrapped-function fix is allowed with the switch off because Ticket 22 proposes it for `main`. The unresolved-name change is a breaking change: today the build raises `NameError`, afterwards the build succeeds and execution fails with a different error. It needs migration instructions in the document's main part. Dropping `typing_inspect` from the dependencies and raising the `typing_extensions` floor change what an install provides, and need instructions too.
- Ticket 22 fixes the same wrapped-function failure on the 1.x line with a small patch and brings it into `2.0`. This Ticket does not wait for it. Whichever of the two lands second keeps the other's regression tests passing.
- The plan assumes `typing_inspect` is abandoned: its last release was in 2023-05. That was inferred from the release date and not verified. It also assumes `typing` and `typing_extensions` cover every call. If a call has no equivalent, say so in the pull request; the dependency can return, and the boundary module still stands.
- `hamilton/experimental/h_cache.py` calls `typing_inspect` and is outside the region. Once the core no longer depends on `typing_inspect`, that module fails to import in a plain install. Convert it or give it an optional dependency; do not leave it broken.
- The core declares `typing_extensions > 4.0.0` today. The outline names `typing_extensions>=4.13` as the path to format-aware `get_annotations`, `Format` and `evaluate_forward_ref`. Declare the lowest version the boundary really works with, and prove it by running the boundary's tests with exactly that version installed.
- The outline warns that the backport "approximates `FORWARDREF`/`STRING` behavior on older interpreters; it does not reproduce deferred annotation execution on 3.11." The floor is Python 3.11 and the CI matrix goes up to 3.15, where annotations are evaluated lazily. Test the boundary at both ends.
- Do not match unresolved annotations by their text. The outline: "identical text can name different types, and different aliases can name the same type." Keep the namespace with the unresolved name.
- Node construction passes the function's globals to `get_type_hints` only on Python 3.13 and later. Read what that version branch was for, in its commit and pull request, before you move or remove it.
- The search test is textual, so it also meets things that are not reads of a function's annotations: `get_type_hints` called on classes (dataclass fields of data adapters under `hamilton/io/`, `TypedDict` fields in the decorator that extracts fields) and writes to `__annotations__` (the materializer factories, the function copier in `hamilton/ad_hoc_utils.py`). Decide how the test treats them, encode that in the test, and say it in the pull request. Routing the class reads through the boundary keeps the test simple.
- `ui/sdk`, `dev_tools/language_server`, `hamilton/plugins/h_mcp`, `hamilton/cli`, `contrib` and the plugins use the core's type helpers. Find the callers of each helper before you change it, and keep the public helper names in `hamilton/htypes.py`.
- Before a structural change to a file over 300 lines (`node.py`, `htypes.py`, the larger decorator modules), remove its dead code, unused imports and debug logs in a separate commit. For a rename, search separately for calls, type references, string literals, dynamic imports, re-exports and tests.
- For the build-time measurement, fix the number of runs before you read a result. A gain larger than hint resolution's share of build time is a measurement fault until you can explain it.

## Suggested approach

This is advice; discard it if you find better. Build the boundary on `typing` and `typing_extensions`: one function that takes a callable, unwraps it to find the namespace of the function the user wrote, and returns the resolved parameter and return hints with `Annotated` metadata kept, plus the unresolved ones with their text and namespace. Cache the result per function for the length of one build. Replace `typing_inspect` calls in `hamilton/htypes.py` with `typing.get_origin`, `typing.get_args` and small local helpers first, behind the existing helper names, with the suite green after each batch. Write the search test early and watch its list of offenders shrink to none.

## Definition of done

Nothing here is fixed by an owner ruling made for this Ticket. All of it is the plan's working reading of the outline and may be revised on evidence.

The region is every read of a function's annotations under `hamilton/`, excluding `hamilton/plugins/`, `hamilton/contrib/` and `hamilton/experimental/`. A read is: a call to `get_type_hints` or `get_annotations` from `typing`, `typing_extensions`, `inspect` or `annotationlib`; a read of `__annotations__` or `__annotate__`; or a call to any `typing_inspect` function.

- The only such reads in the region are inside the boundary module. A test in the suite performs this search, and it is seen failing on a scratch read added in another module.
- No core module imports `typing_inspect`, and `typing_inspect` is not in the core's dependencies.
- The core declares the lowest `typing_extensions` version the boundary works with, and the boundary's tests pass in a run with `typing_extensions` at exactly that version.
- A function with postponed annotations, decorated by a `functools.wraps` wrapper defined in another module, builds with its parameter and return types resolved against the wrapped function's namespace. A test shows it.
- A name that cannot be resolved is kept with its namespace. Inspection reports it as unknown and the build does not stop. Executing a node that depends on it fails with an error that names the function, the annotation text and the namespace. A test shows each of the three.
- Each function's hints are resolved once per build.
- Build time has a measured verdict: the harness's build scenarios, run for this change and for the commit before it, alternately on one machine, reported as the rule on performance claims requires. The old side is not in the checkout after this change, so run it from the commit before. The item asks for a verdict, whichever way it falls.
